# Japan Life Base 社区升级实施计划

版本：规划稿 v1 · 2026-10-21  
范围：分析附件升级提示词，并结合现有项目确定实施顺序。本轮不修改业务代码、数据库或线上配置。

## 1. 结论与产品决定

附件适合作为长期功能清单，实施时应拆成可独立验收和发布的增量。现有系统已经具备账号、社区发帖回复、独立手机/电脑布局、Markdown 新主题编辑器、图片、标签、草稿、基础后台及电费工具。继续沿用当前 Node.js、SQLite 和静态前端，扩展已有组件。

用户已确认本次语言规则：**首次默认中文；界面人工翻译；帖子由用户点击翻译。**

明确执行以下规则：

- 首次访问默认简体中文，浏览器语言只用于提供切换建议，不自动替换默认语言。
- 简中、繁中、日语、英语、韩语的界面文案继续人工维护。繁中已存在，应保留。
- 用户明确选择其他语言时，沿用自动翻译与标识；不能以此覆盖人工维护的界面字典。
- 登录用户的语言偏好保存到账号，未登录用户保存在浏览器。主动切换立即生效；首次登录同步偏好时保留当前路由、阅读位置和编辑内容。
- 用户帖子保存原文，所有语言均可由读者点击翻译，并标注“自动翻译”、提供“查看原文”。人工界面翻译和用户帖子翻译使用分离的流程。
- 原文语言不直接等同于发帖时的界面语言；允许作者指定，识别不确定时保留未知状态。
- 首批不启用帖子默认自动翻译。未来若增加此选项，仍以用户明确设置为准。

本计划依据附件全文、当前本地源码、维护 skill 和项目部署记录，辅以前后端独立只读审查。本轮没有重新运行测试、连接 VPS、读取生产数据库或验证实际在线版本。

部署文档最新记录为 `20261021T030013Z-sitemap`，记录最近一次本地 84 项测试通过；此前编辑器发布记录为 83 项。本计划不将历史记录表述为本轮测试结果。真实 iOS/Android 输入法、软键盘及辅助功能仍有待验收。

现有维护 skill 的部分测试数和编辑器说明落后于最新源码。实施时同步更新；若文档冲突，以核实后的源码、发布清单和实际服务版本为准。

## 5. 数据与接口设计原则

继续使用现有用户、主题、回复及电费表，不在这次升级中强行合表或更换数据库。新增结构通过有版本的迁移引入，以下为设计方向，最终字段在对应阶段细化。

| 能力 | 主要新增结构/约束 |
| --- | --- |
| 迁移与偏好 | `schema_migrations`、账号语言/时区等偏好；现有 schema 建基线，避免重复执行旧 DDL |
| 楼层与阅读 | 保留现有 ID，为回复补不可变楼层号；阅读位置与最高已读分开记录，不因删除重新编号，最高已读不被另一设备旧状态倒退 |
| 编辑与翻译 | 内容版本/修订记录；编辑带版本校验；译文键包含内容版本、目标语言及翻译规则版本 |
| 通知 | 统一事件、接收者、去重键、已读状态、订阅；和内容写入保持事务一致，首批只做站内通知 |
| 反应/收藏 | 数据库约束每用户每帖一个当前反应；收藏仅本人可见，笔记和提醒作为后续扩展 |
| 最佳答案 | 仅关联同主题中的可见回复；作者/管理员可选择、取消、更换；隐藏/删除后同步处理已解决状态 |
| 分类与标签 | 稳定 ID 与现有值回填；停用优先于删除；禁止删除被引用目录后留下无效帖子 |
| 用户名与隐私 | 新增稳定公开 handle，设计已有昵称冲突处理；不用邮箱作为公开标识，不把可改昵称当关联主键 |

所有列表、搜索、引用、翻译、通知、图片与分享接口统一检查内容可见性，管理员隐藏的内容不能从其他入口读到。

封禁/禁言还须覆盖已有登录会话和所有相关写入口：封禁后旧会话不能继续操作；禁言至少覆盖主题、回复及内容编辑，不能只隐藏发帖按钮。上传、举报、翻译等独立接口逐项定义允许/禁止规则。管理操作需防止误封自身或最后一名管理员，并测试权限变更即时生效、重启后仍生效。

## 6. 帖子翻译专项

不能直接移除现有翻译接口对人工语言的限制，否则会混淆界面人工维护和帖子按需翻译。

1. 单独提供按主题/回复 ID 请求翻译的服务端接口，先检查权限，再取得原文；不把任意私密字符串提交到公共翻译接口。
2. 点击后才请求正文翻译；列表不批量翻译全部长正文。保留已有并发控制、总预算和请求去重，增加账号/匿名来源限额。
3. 对 Markdown 解析后的文本节点翻译，保留代码块、行内代码、链接地址、图片关联、金额和其他需要保护的数值。结果继续走安全渲染。
4. 展示原文语言、自动翻译标识、切换原文、失败重试；失败时仍能阅读原文。
5. 原文编辑后使用新版本缓存，不出现旧译文冒充最新内容。引用同时保留来源 ID 和引用时的文本版本。
6. 翻译供应商、密钥、超时及额度在服务端管理。以后若新增私信，默认不翻译私人内容，单独设计明确的用户触发与权限。

## 7. 布局与浏览体验

保留现有品牌和布局比例，借鉴参考论坛的阅读路径。参考：[论坛使用指南](https://teskas.net/t/topic/20363)。

- 桌面继续使用左侧约 260px 导航与充分利用剩余宽度的内容区，不能为了手机适配而统一收窄；时间轴等辅助列按宽度和长帖需要展示。
- 发帖相关操作继续位于左侧；小工具入口放左栏“内容”分组上方，保留“频道：杂谈”及内容底部联系入口。
- 手机单独设计导航、话题列表、回复编辑和软键盘下的操作位置；菜单通过抽屉打开，发帖入口保持清楚可达。
- 列表保留高密度、清晰标题和少量辅助信息。新增未读、已解决和通知时，避免堆满标签。
- 切换语言、翻译、返回列表不丢阅读位置或草稿；长帖只加载需要的楼层。
- 加载、空数据、提交中、失败重试、权限不足均有明确状态。真实手机输入法和屏幕阅读器作为单独验收。

## 8. 搜索与 SEO 的实施边界

基础服务器搜索在 M2 解决“只能搜到已加载内容”的问题；M5 再增加相关性和完整筛选。优先验证 SQLite FTS5，而非引入额外搜索服务。当前本地 Node 运行时具备 FTS5，VPS 上仍须核实。

中文、日文与韩文需要专门样本验证。FTS5 trigram 对不足 3 个 Unicode 字符的全文匹配存在限制，短词须设计受限回退及性能测试，不能只打开 FTS5 就宣称完成多语言搜索。依据：[SQLite FTS5 文档](https://www.sqlite.org/fts5.html#the_trigram_tokenizer)。

SEO 提前到 M2 做基础工作：真正的路径详情、可抓取原文 HTML、正确状态码、canonical 和公开话题 sitemap；旧 hash 链接由浏览器兼容解析。Google 建议用 History API 路径表达不同页面内容，不能仅依靠片段地址。依据：[Google JavaScript SEO 文档](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)。

后续仅为真实维护的多语言页面增加匹配的 metadata/hreflang；用户帖子以原文地址为主，机器译文不批量生成可索引地址。依据：[Google 多语言页面指南](https://developers.google.com/search/docs/specialty/international/localized-versions)。

## 9. VPS、备份与电费工具

附件的 VPS 配置写成 2 vCPU/2GB，现有项目记录为约 3 vCPU/2GB；实际硬件留待实施前只读核实。当前社区服务还有独立内存限制，设计以实际服务限制和共享主机余量为准。

- 保持 Node.js + SQLite 单体部署，先优化查询、分页、索引、媒体配额与缓存。没有测量证据前不增加 Redis、PostgreSQL 或搜索集群。
- 图片目前作为数据库 BLOB 备份。补全已发布媒体配额和容量监测；增加任意文件附件前先评估存储及滥用控制，不照搬参考论坛上传策略。
- 使用当前真实库的受控副本验证迁移与备份恢复；不得在生产添加测试账号或帖子进行验收。
- schema 变化后的恢复方案必须考虑代码兼容和新写入数据。优先兼容版本或前向修复，不能直接覆盖旧数据库而丢失新帖子。
- 保持 `www.jp-lifebase.com` 主站和 `jp-lifebase.com/denkikakaku` 工具路径及现行最近 6 个月查询限制。
- 不修改电费单价、计算规则、数据版本或排序。社区引用/分享结果仅包含必要的地区、月份、套餐、容量、kWh 与数据版本，不含个人身份信息；过期月份的分享页不绕过 6 个月限制。
- 同一 SQLite 中的社区升级必须回归电费模块和共享备份，不能只检查社区健康页。

## 10. 每期验收与发布流程

1. 写清本期范围和不涉及范围，更新任务状态，不用截图替代持久化与权限验证。
2. 在现有源码基线开发；对旧库副本执行迁移，验证可重复执行、记录保留和外键完整性。
3. 运行与改动相关测试，再执行现有整套回归；通过前不发布。
4. 分别验收电脑和手机：宽布局、菜单、输入法选字、软键盘、预览、错误恢复、语言切换、返回位置。
5. 覆盖旧账号、旧 plain 内容、重复提交、跨账号访问、隐藏内容、分页边界及电费回归。阅读/通知另测多设备竞争与去重。
6. 发布前备份，发布后验证真实版本、页面、权限及工具；明确可用恢复路径。
7. 更新实施记录和维护 skill，记载实际通过的检查及仍未验收的项目。
