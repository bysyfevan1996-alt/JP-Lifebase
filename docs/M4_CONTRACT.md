2026-10-22. Implement after the editing improvement; publish two notes V1.3/order130 and V1.4/order140. Keep M2 pending and no email/push/private messaging. Native Node24/SQLite, no new services. Freeze migrations1–3; new migration4 only. Production data never used for test posts.

## Editing improvement (root)

Public original and reply metadata shows editedAt as an absolute localized date/time in a real time element, plus version. Owner/admin history stays permission limited, with paginated versions (50 per page, beforeVersion), latest/current/original labels, editor and absolute time, safe rendered preview and original text toggle. Never lose conflict/manual merge or original plain format. Hidden history stays unavailable. No public disclosure of old revisions.

## M4 HTTP (backend owner)

All new writes require current signed-in account, same Origin, `expectedUserId` matching current account, reread account after await, banned blocked. Muted cannot react/set answer (public interactions); may change own subscription/bookmark/mark notifications read. IDs are existing content IDs `{kind:'topic'|'post',id}`, first post uses topic.id. Hidden topics/replies excluded from all reads/counts/notifications/answers/bookmarks. Notifications hold references, not copied body/excerpts; metadata fetched only after visibility checks.

- `GET /api/me/identity` -> `{identity:{id,name,handle}}`. Stable public handle generated lazily for every user (old records preserved), ASCII lowercase `[a-z][a-z0-9_]{2,31}`, deterministic non-email ID/hash base, collision safe. Stored in separate `user_handles` table with unique nocase, not new positional user columns. No rename UI. `GET /api/users/mentions?q=<prefix>` logged only, nickname or handle prefix (Unicode text, min2/max32, controls rejected), max8 results `{users:[{id,name,handle}]}`, no email/private data. Sender sees own handle in left account panel. Mention body plain visible text token `@handle`, code, quoted block and link URL must not generate mentions; at most20 distinct targets.
- `GET /api/me/notifications?cursor=<opaque>&unread=1` -> `{notifications:[{id,type,topicId,topicTitle,kind,contentId,actor:{name,handle},createdAt,readAt}],unreadCount,nextCursor}` max30 stable `(created_at,id)` cursor; full visibility applied before limit/count, no self notifications. type mention|quote|reply|reaction|answer; priority mention>quote>reply gives ONE notification per event+recipient. `POST /api/me/notifications/read` `{ids:[id...]}` max100 OR `{all:true}` -> `{ok:true,unreadCount}`. Read-all only rows visible at request snapshot, other accounts cannot mark rows. No client timestamp boundaries.
- `GET /api/topics/<id>/interaction` -> `{interaction:{subscription:'watching'|'tracking'|'normal'|'muted',bookmark:boolean,answerPostId:null|string,canChooseAnswer:boolean,newReplies:number}}`. Anonymous allowed normal/false/canChoosefalse. Subscription code defaultnormal; watching notifies all new replies; tracking keeps visible newReplies since last explicit seen and only direct notifications; normal direct own-topic replies, mentions/quotes/reactions/answer; muted suppresses all new notifications including direct. `POST /api/topics/<id>/subscription` `{mode}` -> `{interaction}`. `POST /api/topics/<id>/seen` `{}` updates this account topic seen marker only; normal and watching may also mark seen; do not claim M2 per-post read progress. `newReplies` based on visible reply events after a monotonic AUTOINCREMENT event sequence marker, not total subtraction that can go negative on hide. `POST /api/topics/<id>/bookmark` `{bookmarked:boolean}` -> `{interaction}`. `GET /api/me/bookmarks?cursor=` -> `{bookmarks:[{topicId,title,category,createdAt}],nextCursor}` max30 private, visible only.
- `GET /api/content/{kind}/{id}/reactions` -> `{reactions:{counts:{like:number,thanks:number,helpful:number},mine:null|'like'|'thanks'|'helpful'}}`; public aggregated only, never reactor list. `POST .../reactions` `{reaction:null|'like'|'thanks'|'helpful'}` sets exact desired state idempotently (not blind toggle), ->same. UNIQUE(kind,content,user). Self-reaction forbidden400. Only a genuinely changed new non-null state notifies content author; event key includes actor+content+reaction, repeated toggles cannot spam same-recipient notification. Counts real, survives restart.
- `POST /api/topics/<id>/answer` `{postId:null|string}` only topic author/admin, target visible reply in same topic. -> `{interaction}`. Can unset/change; best answer marking notifies reply author (one per topic+answer target), no self. `GET /api/topics?solved=true|false` filters before LIMIT250. Serialized list topic has `{solved:boolean,answerPostId:null|string}` and detail same; effective answer hidden -> unsolved even when selected id retained for restoration. Do not expose hidden answer ID. Cannot mark first post or other-topic post. Reactions/answer audited where reasonable, no copied text.

## Events/hook contract

New service `createCommunityInteractions` provides `handle`, `onTopicCreated({id,userId,body,bodyFormat})`, `onReplyCreated({id,topicId,userId,body,bodyFormat,quotes})`, `onContentEdited({kind,id,topicId,userId,body,bodyFormat,version})`, and `topicState(id,user?)`. Hooks run SYNCHRONOUSLY INSIDE existing creation/edit transaction BEFORE commit; do not open nested transaction. Creation replay must not run hooks; unique event/recipient DB constraints and no self/correct mode. Edit only notifies newly added mentions once per content+target, never re-notify unchanged mention on every save. Non-mention modifications no new reply event. A durable event entry can fan out multiple recipients but only one visible notification each. Hidden content dynamic filtering applies even after previous event/read. Startup does not send old events or generate notifications for legacy posts.

Backend agent owns `community-interactions.mjs`, `interaction-mentions.mjs`, `migration-v4.mjs`, `schema.mjs`, `server.mjs`, hooks in `topic-posting.mjs`, and `community-content.mjs` EXCEPT history function (root). Expose hook via `interactions` optional param to content/posting constructor; preserve standalone tests. Root modifies history, frontend edit metadata, docs/announcements/install/version. Agent coordinate community-content edits in minimal areas, do not replace full file.
