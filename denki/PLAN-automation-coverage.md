## 2. 整体设计

继续使用现有 Node.js 24+、SQLite、VPS 和页面，不更换技术栈。分开维护以下对象：

| 对象 | 内容与用途 |
| --- | --- |
| 供应商 provider | 公司身份、官方资料入口；代理品牌与实际供电合同关系另列 |
| 电网区域 area | 东京、中部、关西等；与都道府县分开 |
| 地区版套餐 offer | 供应商、合同版本、区域、容量条件、可售状态与有效期 |
| 计费规则 revision | 基本费、阶梯、最低料金、燃调公式、舍入规则及生效条件 |
| 月度资费 tariff | 地区版套餐、规则版本、料金月、月度调整、补贴和证据 |
| 供应覆盖 coverage | 套餐适用网区、官方列明的地域例外、核验日期、适用期与来源；前期不建设地址级查询 |

邮编库和地址到网区的映射不作为当前数据结构改造的必需部分，全国覆盖后再按实际需要设计。

规则和月度数值分开，历史版本继续保留。使用明确的生效日期与供应商料金月规则，不能把发布日、自然用电月或付款月混作适用月。跨月遇到规则变更且现有输入无法判定时，要求必要条件或排除，不把新规则套到整个旧账期。

新增 `schemaVersion`，缺失该字段的已发布快照按旧格式处理。通过只读的内存适配器及必要的版本化计算策略兼容旧格式；保存的原始 JSON、hash 和旧证据不重写、不重新序列化替换。历史结果也要绑定相应计算规则，不能因引擎升级悄然变化。以实际保存的 V1/V2 原始快照验证目录和比较接口，公共接口继续执行实时六个月窗口，旧月份仅作内部复现验证。

## 3. 月度自动获取

流程：**定时检查官方来源 → 保存原件 → 提取候选数据 → 自动核验 → 差异报告 → 复核 → 新版本发布 → 线上核验。**

### 3.1 抓取哪些内容

- 每月：各供应商、各网区、各合同规则对应的燃料调整单价及补贴适用信息。
- 每年或政策变动时：再生能源附加费及其适用期、政府补贴安排。
- 不定期：基本费、阶梯价、约款、税与舍入规则、附加调整项目、供应范围、新申请状态和停售通知。

每家供应商有独立的来源配置和解析器。优先采用官方结构化资料，其次 HTML 表格、PDF；官方页面直接链接的托管文件也需保存其来源关系。不能仅按月份猜测 PDF 地址后当作已证实公告。不能因为不同公司某几个月数字相同，就长期共用一个燃调数据源。

### 3.2 调度与证据

- 建议 VPS 上设置每日日本时间 06:00 的数据检查任务，失败有限重试；它是本计划的待实施项。
- 公告可能提前或延后发布，应每日检查，不能只在每月 1 日抓一次。未来月份先入候选库，公共比较仍限制最近六个月。
- 根据响应类型与文件内容识别 HTML/PDF，不以链接是否以 `.pdf` 结尾判断。
- 原文件按内容 SHA-256 保存，每次抓取记录独立追加；保存请求网址、最终网址、获取时间、公告日期、页码、地区、套餐与适用期。可变网址换内容时保留前后原件。
- 原件、内容索引和抓取日志置于发布包之外的持久目录，部署或回滚不清空。现有备份只覆盖 SQLite，P1 需把数据库引用与原件纳入一致的备份集合并验证恢复；恢复后核对每个来源引用及 hash。已发布版本引用的证据长期保留，未引用候选按明确保留期清理，不沿用数据库每日备份份数来删除历史证据。
- 抓取与发布分开运行。抓取任务仅写原始资料和候选记录，不能直接覆盖公开资费或已发布证据。
- 记录每家公司每个月的完成度、最近成功抓取时间、解析结果、待处理原因。没有新内容时保持安静，有缺月、失败或规则变化时给维护者汇总；实施通知渠道时再按已授权渠道接入。

### 3.3 自动校验与发布门槛

候选数据至少校验：

1. 供应商、套餐版本、区域、料金月、适用期和来源一致；规则区间无冲突，来源引用能解析。
2. 基本费、阶梯、燃调、补贴、再生能源费、附加费用、税和舍入信息齐全；净燃调不能重复减补贴。
3. 费率使用定点数；变化幅度与上一版本对比。涨跌阈值只触发复核，不能作为“正确”的证明。
4. 与官方独立算例或独立人工计算一致；已有四个套餐的历史结果不变。官方算例含付款折扣时先统一计算条件。
5. PDF 有表格、脚注、隐藏旧文字或解析冲突时，检查渲染页面；解析不确定时不发布。
6. 发布产物包含预期版本、目标月份、套餐覆盖清单和证据；发布后核对线上版本与已知算例。

首版采用**获取、提取、校验、出报告自动化，发布前人工复核**。先并行运行至少 2–3 个料金月，积累漏抓与误解析记录；之后只允许规则稳定、资料齐全的月度参数进入自动发布白名单。新供应商、新规则、来源模板变化、异常修订仍需复核。

首版沿用现有发布过程：候选数据经复核生成新的数据版本，再打包上线；不同时引入生产热更新。后续确有需要时，再增加事务化的当前版本切换。

失败时保留已核实的历史资费，明确显示目标月“待更新”；缺资料的套餐逐项排除。不用上一月单价填新月，也不宣称覆盖所有供应商。

### 3.4 需要优先消除的现有隐患

- 共享基本费表不能原地修改，否则会影响其他公司和历史月份；应按套餐、生效期保存独立规则。
- TEPCO 当前一份约款记录有效至 2026-10-31，新增后续月份前要确认新约款。
- Tokyo Gas 来源选择有 `month === '2026-10'` 的特殊判断，直接追加 11 月可能选回旧来源；改为按生效条件选择并校验覆盖。
- 当前归档脚本会重写 `index.json`，不应把它当作逐次不可变抓取日志。

## 4. 如何增加供应商

目前同类普通住宅安培阶梯套餐可以继续人工增加，但应以**具体地区版套餐及合同版本**为接入单位。

1. 确认实际供应商、代理渠道、套餐版本、官方供应范围、容量条件及是否接受新申请。
2. 收集完整价目表、约款、月度调整、补贴、再生能源费和官方算例；新增套餐、规则与来源记录。
3. 在最近六个月内按实际核验结果补月度数据；允许只覆盖其中部分月份，逐月显示可用状态。
4. 建立容量、地区、合同与账期适用判断；不适用的候选套餐单独排除，不能让一个不支持 10A 的套餐导致整个比较失败。
5. 核对代表性官方算例、阶梯边界和舍入，归档证据，发布新版本，并接入后续抓取配置。

优先增加 2–3 个资料齐全、与现有计算模型相同的套餐。第一批品牌名单在资料审查后确定，避免先显示公司再补价格。Octopus 作为后续单独一批：先补齐实际账期天数、套餐版本、燃调与舍入，再开放；不能默认一个月 30 天。

区分“能算历史账单”和“现在能切换申请”。已停售的旧合同可以作为当前账单基准；不能因此列入可新申请推荐。历史月份排名应写明是按该月条件比较，不把历史差额包装成未来节省保证。

当前修改入口：[套餐与费率](D:/2.Work/7.JapanLifeBase/sites/community-home/denki/data.mjs:29)、[计算与适用校验](D:/2.Work/7.JapanLifeBase/sites/community-home/denki/engine.mjs:13)。长期把品牌、地区版套餐、计费规则拆开后，新接入主要是资料配置、解析器与验证样例。

## 5. 如何增加地区

前期由用户依据账单手动选择供电网区，目录只开放已经支持计算的区域；套餐按网区、月份、容量与合同条件筛选。保留官方地域例外说明，暂不建设邮编查询、地址解析或地址级可签约确认。

建议顺序：

1. 明确现有东京网区与各套餐的适用条件，页面名称说明为“东京电力区域”，避免被理解为仅东京都。
2. 增加中部等较接近现有安培阶梯模型的地区，先做当地基础套餐与至少一个可比套餐。
3. 增加关西等需要新计费模型的地区，之后按实际需求逐区扩展。

都道府县不能直接等同网区。TEPCO 官方区域说明中，静冈以富士川东西划分，岐阜、三重等也有部分地区的边界差异；每个零售套餐还可能有自身例外。[官方区域说明](https://www.tepco.co.jp/ep/private/plan/index-j.html)

关西従量電灯A包含最初 15kWh 的最低料金，燃调与再生能源费也有首段对应计算方式；它不是把东京基本费换个数字即可支持的模型。[关西官方套餐与算例](https://kepco.jp/ryokin/menu/dento_a/)

## 6. 全国覆盖后：可选的邮编网区定位

邮编功能的目标是帮助用户自动选择东京电力区域、中部电力区域等供电网区。全国计费覆盖之前不实施，也不预先导入全国邮编库或建设位置查询接口。

全国覆盖完成后，再评估是否实施以下流程：**输入 7 位邮编 → 定位供电网区 → 自动选中区域 → 按原有流程选择当前套餐并比较。** 实际签约的零售供应商与套餐仍由用户选择，不由邮编推断。

届时可使用[日本邮便官方数据](https://www.post.japanpost.jp/service/search/zipcode/download/utf-zip.html)取得地址信息，再结合官方电网区域资料维护映射。日本邮便数据本身不包含电网边界；多地址、跨网区或离岛等不能确定的情况，继续让用户按账单手动选择。邮编解析只用于填写区域，最终比较输入仍以用户确认的网区为准。

这项后期功能保留手动选区，不增加地址级供应商可签约查询；数据来源、版本、更新周期与边界用例在该阶段再具体设计。
